About

An investigator meets a running Linux machine whose encrypted storage is unlocked. Powering it off turns the data back into ciphertext. Keep runs before power-off and decides, for every open dm-crypt volume, one of three things: the volume key can be preserved as evidence and proven correct now, a memory image must be taken first, or only a copy of the mounted files is possible.

Finding the keys is what Keep is for. Two options go with it: Keep can take a memory image of the running system, and it can search a memory dump that exists for the keys and prove them against a disk image.

Keep is not a general artefact collector. It is made to run beside one, such as UAC, and depends on none. It is open-source work for the DFIR community, for lawful examination of systems the examiner is authorised to examine.

What it does

  • It lists every open dm-crypt volume of the system: LUKS1, LUKS2, plain and tcrypt, also LUKS2 with integrity, a volume that cryptsetup is re-encrypting and a volume that carries LVM. For each it says what the volume carries: where it and the devices on it are mounted or used as swap.
  • It backs up each LUKS header, byte for byte the file that cryptsetup luksHeaderBackup writes.
  • It takes each volume key, from the table of the kernel or from memory, and proves it against the header.
  • It takes the memory of the machine as a LiME image, a raw image or the compressed format of AVML, with its SHA-256.
  • It searches a memory dump that exists for keys and proves them against the headers in disk images, or against what the dump itself holds of a header.
  • It writes what it found for a reader, triage.txt, and for a program, verdict.json, with the SHA-256 of every file of the run. A terminal gets the screen in colour, by the SGR sequences for bold and the eight colours alone, and a pipe gets plain lines.[20]

The ideas behind it

The kernel hands out the key

The kernel hands the table of a mapped device to every caller with CAP_SYS_ADMIN, the key of a crypt target in hexadecimal included. No flag asks for the key and kernel lockdown does not withhold it. It is dmsetup that shows zeros in its place unless it is asked.[10] [18] Keep makes the two requests of dmsetup itself, which change nothing in the kernel.

For LUKS1, plain and tcrypt volumes, and for LUKS2 opened with --disable-keyring, the table holds the key. This is the first route, and it needs nothing but root.

A key in the keyring is still in memory

By default cryptsetup gives the key of a LUKS2 volume to the kernel keyring, and the table shows a reference to it. The cipher still needs the key for every block. AES expands a key into round keys,[1] and the kernel holds that expanded schedule as long as the volume is open. Its first 16 or 32 bytes are the key.

A schedule can be found without knowing the key, because each of its words follows from earlier ones by the rule of the expansion. Halderman and others showed this for memory images in 2008, with a search that allows for bits that have decayed.[2] Keep reads the memory of a running machine, where no bit has decayed, so its test is exact: every position is tested over the whole schedule, 176 bytes for AES-128 and 240 bytes for AES-256. A hit is a real schedule, though not necessarily one of a disk volume.

With aes-xts the volume key is two AES keys, the data key and the tweak key. On x86-64 with the AES-NI family of drivers the kernel keeps both schedules in one structure, the tweak schedule first and the data schedule 496 bytes after it.[12] Keep pairs the schedules by that distance, and in the search of a dump it tries every other pair after those.

The memory is read through /proc/kcore, which needs root and is refused under kernel lockdown in the mode confidentiality.[11]

Only a proven key counts

Nothing is reported as a volume key on the strength of where it was found. A LUKS header stores a PBKDF2 digest of the volume key: LUKS1 in its binary header, LUKS2 in the object digests of its metadata, which are JSON.[3] [4] [6] [9] A key whose PBKDF2 output equals the stored digest is the volume key. Keep computes that itself, with its own SHA-1, SHA-2 and HMAC,[7] [8] which it tests against the examples of the standards at every start.

A header whose keyslots were erased with cryptsetup erase keeps its digest. A key from memory is still proven against it, and is then the only way into the volume. Plain and tcrypt volumes have no digest, so their keys are captured and cannot be proven on scene.

A header can lie in memory too

Nothing in the kernel keeps a LUKS header: dm-crypt is given the key and the cipher, and cryptsetup reads the header past the page cache where it can.[5] [10] What a machine holds of a header is what else read it. On a guest with Ubuntu 24.04.5, udisksd held the whole metadata of an open LUKS2 volume in its memory a minute after the volume was opened.

So the search of a dump looks for a LUKS1 header at the start of a page and for the digests of a LUKS2 header, and proves keys against them. From such a dump alone, with no disk image, Keep proved the volume keys of the open containers. This is seen on one guest and on one machine with Linux Mint 22.3. Whether a system without udisks2, as a server installation, holds these metadata is not known.

The keys first, then the image

An event can close the window of the keys within seconds. An image of the memory takes longer, 16 s for 16 GiB on one machine and up to 73 s on the machines of the pipeline. So the keys are taken first. A key counts as captured only when it is written to the destination and flushed, because the machine may lose power the moment the verdict is read.

An image that does not overwrite what it reads

A file that is written in the usual way goes through the page cache: the kernel takes free memory for its pages, and what lay there is gone. Free memory is where the remains of earlier work lie, and an image of a large machine is a large file. Keep writes an image with direct writes, from the memory of the program to the device, where the file system of the destination has them, and lets the pages of a flushed file go.[13] In the runs of the pipeline no page of any image lay in the cache after the run.

The memory is read as AVML reads it, the ranges that /proc/iomem names as RAM through /proc/kcore, and the formats are those of LiME and AVML with the framed Snappy stream.[14] [15] [16] AVML itself converts the images of Keep, byte for byte to the files that the formats define. banners.Banners of Volatility 3 has read one of its LiME images.[17]

One file that starts nothing

Keep is one program, linked statically against musl.[19] It starts no other program, loads no library and reads a file of the examined system as text only. The programs of the examined system, which an examiner cannot trust, take no part in the run, and the run adds one process to the memory it is about to image.

Because it asks cryptsetup nothing, it takes none of its locks. On a volume whose re-encryption was paused in a step, cryptsetup status waited without end, and Keep read the same volume and proved both of its keys.

Safeguards

  • No key is printed. On screen and in every report a key is named by its length and the first 16 digits of its SHA-256.
  • Volume keys and the lists of schedules, which are key material too, are written only below a keys/ directory, with umask 077.
  • Keep writes into the destination directory and nowhere else, and what it asks of the kernel changes nothing there. No name of the examined system is used in a file name as it is.
  • The memory of the process is locked, so that no key reaches the swap space, and the process writes no core file.
  • A control character in a text of the examined system, as in the name of a mapping, is printed as a space.
  • The search of a dump and the lab tools only read the dump and the images they are given.

Known limits

  • x86-64 only. The pairing of the XTS halves on scene assumes the layout of the AES-NI family of drivers. With another implementation of XTS the run ends with needs a memory read, and the search of the image tries every pair.
  • The search of memory finds AES keys only. A volume with another cipher has no memory route.
  • Kernel lockdown in the mode confidentiality blocks /proc/kcore, and with it the memory route and every image.
  • Keep covers dm-crypt only. Mounted file systems that encrypt by themselves (eCryptfs, ZFS, gocryptfs, CryFS, EncFS) are named in the report as not examined.
  • A LUKS2 volume with integrity whose key is in the keyring ends with live copy only: its volume key holds the key of HMAC, which is no AES key. With the key in the table it is captured and proven.
  • A header whose digest uses ripemd160 or whirlpool is backed up, and its key is proven in the lab by vkverify.py, not by Keep.
  • The search of a dump reads header backups, raw images and devices. The disk file of a virtual machine and an EnCase image are read by vkverify.py.
  • A digest that a dump holds and has no key for costs every pair of the keys of the dump: 510 s for 90 keys on one machine. These attempts come last, and their number is said before they begin.
  • A header backup of a volume that cryptsetup is re-encrypting shows the moment of the run. The header on the device goes on changing until cryptsetup ends.

How it is checked

Every part of the program that reads bytes it did not write is compared with an independent source, and runs with the address and undefined-behaviour sanitizers of the compiler as well: the hash functions with Python's hashlib, the JSON reader with Python's json, the header code and the proof with cryptsetup, the images with AVML and with files that Python writes from the formats.

tests/unit-check.sh

The whole program is checked on real device-mapper and a real /proc/kcore, with volumes made from known keys, on a throwaway guest and never on a machine that matters. The pipeline runs this on every change, on its own two machines and in guests of ten distribution releases. Systems has a card for each.

tests/compat-guest.sh -m /path/to/work fedora-45

A statement on these pages about a kernel, a cryptsetup release or a distribution comes from the source of that version or from a run, and says which.

Version 1 and version 2

Keep 1 is a shell script, keytriage.sh, on a tool medium with a static bash, busybox, the scanner and AVML. It uses the dmsetup and the cryptsetup of the examined system. Keep 2 is the one C program of these pages, which does the work of that medium and starts no program.

Version 2.0 is not released. These pages describe keep 2.0-pre9. The script is in the repository beside it, and the pipeline runs both on the same volumes: the C program must write the same line of the report for every volume, and header backups and keys that are the same byte for byte.
