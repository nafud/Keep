Keep

Decryption-readiness triage for an unlocked Linux system

An investigator meets a running Linux machine whose encrypted storage is unlocked. Powering it off turns the data back into ciphertext. Keep runs before power-off and decides, for every open dm-crypt volume, one of three things: the volume key can be preserved as evidence and proven correct now, a memory image must be taken first, or only a copy of the mounted files is possible.

Finding the keys is what Keep is for. Two options go with it: Keep can collect a memory dump of the running system, and it can search a memory dump that exists for the keys and prove them against a disk image.

Keep is not a general artefact collector. It is made to run beside one, such as UAC, and depends on none.

Quick start

1. Build the tool medium

On a Debian or Ubuntu workstation. The medium is what runs on scene, so that the triage does not depend on the programs of the examined system.

git clone https://github.com/nafud/Keep.git
sudo apt install bash-static busybox-static xorriso gcc curl file
./build-toolkit.sh /path/to/work

This writes work/tools/ and work/tools.iso with the volume label KEEPTOOLS. The medium carries a static bash, a static busybox, the scanner kcore-keyscan, keytriage.sh, keep-menu.sh, the launcher keep and Microsoft AVML v0.21.0, which is accepted only when its SHA-256 equals the value pinned in the script. dmsetup and cryptsetup are not on the medium. The examined system's own are used, and their paths and SHA-256 go into the report.

2. On scene

Keep is started from the tool medium, here at /media/tools, in the directory that is to take the output. It asks for every parameter in the manner of ewfacquire: a question shows its choices in parentheses and its default in square brackets, and Enter takes the default. Enter at every question searches the running system for keys and writes into the current directory. With -n it asks and lists everything and runs nothing.

sudo /media/tools/keep

The destination is the examiner's decision. Keep asks for it, offers the current directory, and does not test where it lies. A memory dump is taken after the keys, because an event can close their window within seconds and an image of a large machine takes minutes. Compressed, it is for a destination with less free space than the machine has memory. How much that saves depends on what the memory holds: in the five runs of the pipeline that took it, the image had 85 % to 87 % of the size of the memory.

keep is a small static program of the medium. It starts the dialogue in the medium's own shell with -p, which keeps the environment of the examined system's root shell out of the scripts, and they refuse any other start. The script that does the work takes the same parameters as options, for a run without questions: the keys into the current directory, or into the directory of -d, with -m a memory dump and with -m -c a compressed one.

sudo /media/tools/bin/bash -p /media/tools/keytriage.sh -d DIR -m

One verdict is printed per volume, with what the volume carries: where it and the devices that stand on it, such as logical volumes, are mounted or used as swap. An example of the screen, shortened, with illustrative values:

3. In the lab

For a memory dump that exists. Keep asks for it when dump is the answer to its first question, and the script behind that answer can be run by itself. The dump is searched and every LUKS header in the disk images is located and tested. A disk image may be raw, an EnCase image (E01) or the disk file of a virtual machine. The lab tools need Python 3 and the scanner, and they only read their inputs.

./offline-keyscan.sh -k /path/to/work/tools memory.lime disk.dd

The result is a folder scan_<dump>_<UTC time>/ with one NAME.vk per proven volume key, for cryptsetup open --volume-key-file. The report in it is printed as text, and several reports are compared in one table:

python3 -I keep-report.py scan_*/verdict.json

The two steps of offline-keyscan.sh can be run by hand:

kcore-keyscan [-s STEP] [-r] [FILE]
python3 -I vkverify.py CANDIDATES [HEADER...] [--image DISK]... [--out DIR] [--json FILE]

Verdicts

keytriage.sh prints exactly one of these per volume. They are also the values of verdict in the report.

VerdictMeaning
captured and provenThe key is written to the destination and opens the LUKS header.
captured, in useThe key is read from the live table of a volume without a header digest (plain, tcrypt). Opening the image in the lab confirms it.
captured, not provenA key is read, but there was no header backup or the header refused it.
needs a memory readThe key was not reached in this run. A memory image keeps the route open.
no key neededThe mapping has no key: its table line names a key of size 0, which is the null cipher. The device holds the data as they are.
live copy onlyNo key route is open: a non-AES cipher behind a keyring reference, kernel lockdown confidentiality, or a refused read of /proc/kcore.

key held no key needed action needed no key are the four classes that keep-report.py prints beside each verdict.

How the key is reached

For each mapping of dmsetup ls --target crypt the script reads cryptsetup status and the kernel's own table line, and takes the first route that is open.

RouteWhenWhat happens
R1 tableThe table line carries the key in hexadecimal: LUKS1, plain, tcrypt, and LUKS2 opened with --disable-keyring.The key is written to keys/NAME.vk and, for LUKS, proven against the header backup.
R3 memoryThe table line carries a keyring reference. This is the default for LUKS2, including systemd-homed.kcore-keyscan searches /proc/kcore once for all volumes. Candidates are proven against the header backup. The list of the schedules is kept in keys/ also when there is no header backup, because the lab verifier can prove from it.
R5 liveNo key route is open.Only a file-level copy of the mounted plaintext remains.

A memory image is the fourth route, R4. It is searched in the lab with the same scanner.

The cipher is taken from the table line. aes-xts-* and capi:xts(aes)-* are XTS, where the volume key is two AES keys. Any other aes-* is a single AES key. Everything else has no AES schedule of the volume key, so the memory route does not apply.

The proof

A candidate key counts only when it is proven. Nothing is reported as a volume key on the strength of where it was found.

  • On scene the proof is cryptsetup open --test-passphrase with the key file and the header backup, run by the examined system's own cryptsetup. The key option is --volume-key-file where the installed release lists it, and --master-key-file otherwise.
  • In the lab vkverify.py computes the proof itself, with no cryptsetup and no loop device. A LUKS header stores a PBKDF2 digest of the volume key: LUKS1 in the binary header, LUKS2 in the digests object of its JSON area. A key whose PBKDF2 output equals the stored digest is the volume key. A header whose keyslots were erased with cryptsetup erase keeps its digest, so the key from memory is still proven against it, and is then the only way into the volume.

With --image no header backup is needed. The image is searched for the LUKS magic at sector boundaries, and a place is accepted only when its digest parameters are plausible.

The image may be the disk of a virtual machine. Such a file stores the disk in blocks with a table of where each block lies, and some compress the blocks, so a header does not lie in the file as it lies on the disk. These are read as the guest saw the disk:

FormatWhat is read
qcow2Version 2 and 3, also with clusters compressed by zlib.
VMDKThe sparse extent, also stream-optimized with compressed grains, and a descriptor file with sparse, flat and zero extents beside it.
VDIDynamic and fixed.
VHDDynamic and fixed.
VHDXDynamic and fixed, without a log to replay.

What is recognised and not read is named and is not searched as raw bytes: a qcow2 image that is encrypted, has zstd clusters, extended L2 entries or an external data file, a sparse extent of ESXi, a VHDX file with a log, QED and Parallels. qemu-img convert -O raw writes such a disk as a raw image. A block that only a backing file or a parent disk holds reads as zeros, and that file is named. Each format is checked on images that qemu-img wrote, not on images from VMware, VirtualBox or Hyper-V.

The image may also be an EnCase image, E01, with its further segment files beside it. Its chunks lie in the file compressed or with a checksum behind each, so a search of the raw file finds no header, also without compression. The chunks are decompressed and checked, and a missing or cut segment and a damaged chunk are named. Checked on images that ewfacquirestream of libewf wrote. Version 2 (Ex01) and AFF are named as not read.

Key schedules in memory

AES expands a key into round keys (FIPS-197, section 5.2). The kernel holds the expanded schedule, and its first 16 or 32 bytes are the key. kcore-keyscan tests every position against the expansion rule over the whole schedule, 176 bytes for AES-128 and 240 bytes for AES-256. The test is exact, so a hit is a real schedule, though not necessarily one of a disk volume. That is what the proof decides.

With aes-xts the volume key is the data key followed by the tweak key. On x86-64 with the AES-NI family of drivers the kernel keeps both schedules in one structure, the tweak schedule first and the data schedule 496 bytes after it. keytriage.sh tries only pairs at that distance. vkverify.py tries those first and then every other ordered pair.

The scanner recognises its input from the first bytes.

FormatRecognised byWhat is read
ELF64 coreELF magic, 64-bit, little-endianEvery PT_LOAD segment with a physical address. This is /proc/kcore, and the dump that a hypervisor takes of a guest, checked with QEMU.
LiMEEMiL at the start of each range headerEach range with its start and end address. This is what AVML writes.
AVML compressedAVML and version 2 at the start of each range headerEach range as a framed Snappy stream, with every chunk compared with its CRC-32C. This is what avml --compress and keytriage.sh -m -c write.
rawanything else, or any file with -rThe whole file, with the file offset as the address.
refusedthe first bytes of a kdump, diskdump or flattened makedumpfile file, or of a gzip, xz, zstd, bzip2 or lz4 fileNothing. Such a file holds memory in another form, and a search of its bytes finds a part of the schedules or none.

These are the formats of a Linux memory image that Volatility 3 reads too. An image that is cut, as on a medium that ran full, or damaged is searched up to that place: the schedules before it are listed, the place is named and the status is 1.

What a run leaves behind

In the destination, keytriage.sh writes one folder:

triage_<host>_<UTC time>/
  triage.txt        the screen
  verdict.json      the same verdicts for a program
  headers/          the LUKS header backups
  keys/             the volume keys and the candidate list
  log/              what cryptsetup status, the scanner and AVML wrote
  memory/           with -m: memory.lime (memory.avml with -c), kernel banner, release,
                    os-release, System.map
  manifest.sha256   the SHA-256 of all of them

Every file is created with umask 077. A header backup, the candidate list and a key are flushed to the medium with fsync as soon as they are written, and a key counts as captured only after that, because the machine may lose power the moment the verdict is read. The run ends with a flush of the whole file system of the medium and with status 0, or with status 1 when a write or a flush failed. In the names of the folder and of the files, a character of the host name or of a mapping name that is not a letter, a digit or one of . _ + = @ , - becomes _.

Beside the memory image go the kernel banner, the release, os-release and System.map, which Volatility 3 needs for its symbol table. The image is skipped when the destination has less free space than the machine has RAM plus 64 MiB. A compressed image is started whatever space is free, because its size is known only at the end. Where it cannot be finished, the part that was written is removed and the image counts as failed.

verdict.json has the schema keep-report/1, which vkverify.py --json writes too. A report never holds a key. A key is named by its length and by key_sha256_16, the first 16 hexadecimal digits of its SHA-256.

Known limits

  • x86-64 only. The on-scene pairing of XTS halves assumes the layout of the AES-NI family of drivers. With another XTS implementation keytriage.sh ends with needs a memory read, and vkverify.py can still prove the key from the candidate list, because it tries every pair.
  • The memory search finds AES keys only. A volume with another cipher has no memory route.
  • Kernel lockdown confidentiality blocks /proc/kcore and every memory source of AVML.
  • Keep covers dm-crypt only. Mounted file systems that encrypt by themselves (eCryptfs, ZFS, gocryptfs, CryFS, EncFS) are named in the report as not examined.
  • Plain and tcrypt volumes have no header digest, so their keys cannot be proven on scene.
  • A memory dump is read as an ELF core, a LiME image, a compressed AVML image or raw bytes. A kdump file and a file compressed as a whole are refused. The snapshot formats of QEMU and VMware, which Volatility 3 reads, are not read, and any other container format is searched as raw bytes, which is not tested.
  • EnCase images of version 2 (Ex01) and AFF images are not read.

Safeguards

  • No key is printed. On screen and in every report a key is named by its length and the first 16 digits of its SHA-256. vkverify.py --show-keys is the single, explicit exception, and it does not reach the JSON report.
  • Volume keys and the candidate list, which is key material too, are written only below a keys/ directory, by a process with umask 077, and a key counts as captured only after it is flushed to the destination.
  • Keep writes into the destination directory and nowhere else. Where that directory lies is the examiner's decision, and Keep does not test it: a file written to the storage of the examined system changes that storage, and a key written into one of its encrypted volumes is locked in with the data at power-off. Beside the destination a run changes memory: the programs it starts, and the lock file that cryptsetup creates in /run/cryptsetup while it reads a LUKS2 header.
  • The lab tools only read the dump and the images they are given.
  • The scene scripts run in the medium's static bash, started with -p, with PATH set to the bin/ of the medium and nothing else, and they refuse another shell. The only programs run from outside the medium are the examined system's dmsetup and cryptsetup, by their full paths. Those paths and their SHA-256 are recorded so they can be checked against the distribution's packages afterwards.
  • A file of the examined system is read as text and never executed or sourced. bash -p is part of this: without it the shell runs the file that BASH_ENV names and takes functions from the environment.
  • The downloaded AVML binary is pinned by SHA-256 and refused on a mismatch.
  • The Python tools use the standard library only and are run with -I.

Development

One script runs every check that needs neither root nor device-mapper: the static checks, the scanner on fixtures with known keys and traps, the verifier and the on-scene proof on LUKS headers that cryptsetup makes from the same keys, the verifier on the disk formats of virtual machines as qemu-img writes them, keytriage.sh itself on stand-ins for the examined system's dmsetup, cryptsetup status and /proc/kcore, and the menu through a pipe. The pipeline on GitHub runs it on every push.

tests/selftest.sh

On real device-mapper and a real /proc/kcore the triage is checked on a throwaway guest and never on a machine that matters. The pipeline runs the same check on its two runner images and in guests of ten distribution releases.

sudo bash tests/compat-check.sh

One command fetches a distribution's cloud image, checks it against its pinned checksum, boots it in QEMU and runs the check in it:

tests/compat-guest.sh -m /path/to/work fedora-45

Reports of a distribution where the check passes or fails are welcome as an issue on GitHub.
